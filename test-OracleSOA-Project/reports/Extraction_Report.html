Executive summary

The export is the TaskUs integration estate built by OSI Digital on Oracle SOA Suite 12.2.1.2 (Oracle SOA Cloud Service), with one utility on 12.1.3. It automates the employee lifecycle: Oracle HCM Cloud is the system of record, and new hires, changes, transfers, leave and terminations are pushed to Active Directory, Google Workspace, TeleOpti workforce management, Jobvite recruiting, the EPMS performance system and ADP payroll for the Philippines. Candidates also flow the other way: new-hire files from the recruiting systems (Interviewed / Jobvite) are loaded into HCM through HCM Data Loader.

The export holds about 96 composite projects, but many are copies: an older "SOA_Notification" snapshot of the whole tree, backup (_BKP) and "Copy" folders, and parallel variants of the Google and Jobvite flows. After removing duplicates and unused prototypes, 45 interfaces are worth migrating (18 simple, 16 medium, 11 complex). Most are scheduled jobs driven by a custom database-table scheduler; the rest are reusable services called by those jobs. The source does not show which variant of several services is running in production, so the client must confirm the baseline before the build starts.

Three issues need early attention. First, credentials are stored in clear text across the export (a project readme, SQL scripts, process code, Java classes and lookup tables), including passwords for HCM, Google, Active Directory, WebLogic, ADP and the mail account; these should be rotated regardless of the migration. Second, several processes create accounts with a fixed default password and email passwords to distribution lists, which should be redesigned rather than copied. Third, a large share of the logic is switched off in the code (for example the ADP payroll file upload, TeleOpti updates and several feed readers), and some payroll-related mappings contain defects. The business needs to decide what the target behaviour is before these are rebuilt in Boomi.

Key findings

  • Platform: Oracle SOA Suite 12.2.1.2.0.161003 (productVersion in every composite.xml); Utilities/WebServiceHandler is 12.1.3.0.0. All logic is BPEL; no Mediator, Business Rules (.rules/.decs) or Human Workflow (.task) components exist in the export.
  • About 96 composite.xml files exist, but only about 50 are distinct. SOA_Notification/ is an older snapshot (for example ProcessNewHireEmpReq_Sch.bpel is 774 lines there versus 1,790 in SOA/). Variant trees Employee_JobVite/ and GSuite_Java_Process/ hold later revisions of some services, so the production baseline for those must be confirmed.
  • 45 interfaces are proposed for migration. Excluded as obsolete or non-functional: Employee/CreateUser, Employee/GetAccessToken, "ProcessEmployeeIntReqABCSImpl - Copy", SyncEmpLOVsToXREFABCSImpl (does nothing), ProcessUpdateEmployeeHCMProvABCSImpl (no caller, not in PROD MDS), TimeCardEBS (stub with an unresolvable MDS path), ProcessTeleOptiADPProvABCS (incomplete prototype), all _BKP folders and the SOA_Notification tree.
  • Scheduling is custom: a WebLogic TimerManager servlet (Java/SchedulerServlet) reads table XXTS_SCHEDULING and posts to each *_Sch composite's direct binding; each composite reads and advances its own time window in the same table. Run times are documented in Documents/TaskUs_SOA_Scheduler.xlsx (for example new hire 09:00 and 21:00 UTC). In Boomi these become native process schedules plus a persisted watermark.
  • Oracle HCM Cloud is reached five ways: OTBI logical SQL through a shared wrapper (ProcessHCMExtractSyncProv / ProcessHCMExtractProvABCS, used by about 26 composites), HCM REST and ATOM feeds, SOAP services (FlowActionsService, PayrollProcessingActionService, WorkerService, UCM GenericSoapPort, HCMDataLoader), and BI Publisher reports.
  • MDS: a snapshot of the shared metadata store is included under SOA/Utils/PROD_MDS (also DEV_MDS and DEV_MDS_JobVite). 85 of 88 distinct oramds:/apps references resolve against it. The unresolved ones are oramds:/apps/Provider/ADP/Employee/processemployeeadpprovabcs_client_ep.wsdl (TimeCardEBS), oramds:/apps/Utilities/XSD/EPMSFileWrite.xsd (EPMS _BKP only) and Provider/HCM/processupdateexternalidentifier_client_ep.wsdl (present only in DEV_MDS_JobVite).
  • There are 24 general DVMs and 26 ADP DVMs (for example OUNames 282 rows, CCenter 290 rows, TeleOpti_BU 69 rows) and one active cross-reference (XRef_UCMID: candidateID to UCM contentID, stored in table XREF_UCMID_TABLE whose data is not in the export). These map to Boomi Cross Reference Tables; Credentials.dvm and TeleoptiAuthHeader.dvm hold secrets and must become connection or extension values instead.
  • Disabled logic is widespread: bpelx:skipCondition 1=1 switches off, among others, the ADP payroll FTP uploads, TeleOpti create/update calls, the ATOM newhire and termination feeds, Google user updates on name change, and the Interviewed write-back. Behaviour as exported differs from what the component names suggest.
  • Defects found in the source: the country-lookup SQL in ProcessEmpAssignmentReq_Sch is overwritten; the maternity end-of-leave branch reactivates the people who just started leave; ProcessNewHireEmpBIReq_Sch never advances its window; PayrollWeeks.dvm lookups use column names and keys that do not exist; the ADP master-data XSL takes several values from the first employee for every employee and outputs "0" instead of "000000000" for missing TINs; the TeleOpti BusinessUnit lookup passes a string literal and is always empty.
  • Fault handling is a process-level catchAll that emails EmailDL "notification" (or a hardcoded individual) through XXSendNotification. Most scheduled jobs still advance their window after a failure, so failed windows are never retried. Only ProcessINTReadFileABCSImpl has fault-policies.xml (rejected CSV files are sent to WebServiceHandler, which emails EmailDL "Rejection").
  • 38 Java embeddings (bpelx:exec) and SCA-INF Java classes do password generation, zip/Base64 of HDL files with directory clean-up, Base64 decoding, PGP encryption via a shell script and FTP via a shell lftp command. These map to Groovy scripts or standard Boomi steps (Data Process zip/Base64, PGP Encrypt, SFTP connector).
  • Several services depend on the SOA server file system (/u01/data/domains/SOACS-Pr_domain/...) to pass files between composites and to email attachments. In Boomi these should be in-memory documents; the external drop folders (Interviewed, JobviteFolder) need a Disk or SFTP location.
  • Custom Java web applications also sit in the call path: GSuiteServices (google-restservice-context-root at 129.144.156.126/.139:9073) wraps the Google Admin SDK, and HCMSOAPService (CallHCMRestService) wraps HCM REST with a hardcoded dev URL. Boomi can call Google and HCM directly, so these can be retired.

Integration flow

Source
Oracle HCM Cloud (system of record) and recruiting systems (Interviewed / Jobvite candidate files and REST)
Platform
Oracle SOA Suite 12.2.1.2 BPEL composites, scheduled by a custom XXTS_SCHEDULING servlet, with a shared OTBI query service and an HTML email utility
Target
Active Directory, Google Workspace, TeleOpti WFM, Jobvite, EPMS, ADP GlobalView payroll, and Oracle HCM Cloud itself (HCM Data Loader, Payroll Batch Loader, WorkerService)

Scheduled jobs read HCM changes (OTBI SQL, ATOM feeds, payroll extracts) for a time window and call reusable provider services to create, update, move or suspend identities in AD, Google and TeleOpti, and to produce flat files for EPMS, Jobvite and ADP. Inbound, candidate files and REST pushes are validated and loaded into HCM as HDL Worker.dat files, then reconciled with Jobvite and followed by salary, talent-profile and allowance (PBL) loads. Errors and run reports are emailed to distribution lists.
