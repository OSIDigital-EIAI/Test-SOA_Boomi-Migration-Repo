Purpose

Creates the Active Directory (AD) account for a new hire. Given the employee record from the new-hire job, it reads the worker's department, project, grade, country, job, location and manager from Oracle HCM, checks whether an AD account with that employee ID already exists, looks up the manager in AD, derives the organisational unit (OU) and security group from the project ID, creates and enables the account, adds it to its groups, loads the AD user name into HCM as the Fusion user name, and notifies the manager and HR.

Business context

Gives every new TaskUs employee a network login on day one with the right OU, groups and manager, and keeps the HCM user name identical to the AD account name. Called only by the new-hire job (newhire-emp-sch); the outcome (Success, Existing, Failed) is returned to it and used in its reports.

Summary

This service creates a network (Active Directory) account for each new hire. The new-hire job calls it with the person's ID and name. It looks up the rest of the details in HCM (department, project, grade, country, job title, location, manager), checks whether the person already has an account, and if not creates one in the right part of the directory for their project, sets it active, adds it to the right security group and makes the HCM user name match. The account name follows the TaskUs rule: first letter of the first name, first letter of the last name, then the employee number, all lower case.

Where the account goes and which group it joins are decided by project-ID lookup tables, with separate tables for the US and the Philippines and, in the Philippines, for team leads (grade codes starting "SA-"), agents ("A-") and everyone else. Team leads are also added to the corporate Wi-Fi group. If the project is not in the table the account goes into a general "Floating" area with no project group.

The most important finding is about passwords. Every new account is given the same fixed initial password written into the code, and that password is included in the success email sent to the manager and HR. A random password is generated as well, but it is never set in AD: it is written to the server log and returned to the calling job. This must be redesigned, not copied. Other points to settle: who receives the emails (today a fixed list of named people), what happens when two hires share a name in the same area, and whether a person with a disabled old account should get a new one.

Key points

  • OTBI by Person Number with SET VARIABLE PARAM_EFFECTIVE_DATE='4000-12-31': Department Name, Person ID, Person Number, project ID and description, Location Country and country code, Job Name, Worker Location Name, Manager Name / Person Number / E-Mail, Grade Code.
  • Existence check: LDAP search (&(objectClass=*)(employeeID=<EmployeeID>)) under OU=Users,OU=TaskUs,DC=taskus,DC=prv; an account in "OU=Disabled Accounts" counts as not existing.
  • Manager DN: search by employeeID = manager person number; for Philippine names starting "Ma. " a second search by derived sAMAccountName.
  • OU and group from project ID via US_OUNames/US_ADGroupDNs (country US) or OUNames plus ADGroupDNs_TLS (grade SA-), ADGroupDNs (A-) or ADGroupDNs_Others; Floating OU fallback.
  • Account: DN CN=<First Last>,<OU>; sAMAccountName lower(first character of FirstName) + lower(first character of LastName) + EmployeeID; UPN <sAM>@taskus.prv; userAccountControl 512; pwdLastSet 0.
  • Hardcoded initial password (unicodePwd) is set on every account and included in the success emails; the Java-generated random password is unused in AD, written to the audit trail and returned in the callback.
  • Existing account: only the mail attribute is replaced; status Existing.
  • Success emails go to the manager plus hardcoded individuals; failure notifications are disabled (skipped).
  • Calls ProcessCreateUserDAT (hcm-create-user-dat) and waits for its callback.

Client questions

How should a new employee's first AD password be set and given to them?

Today every account gets the same fixed password, which is also emailed to managers and HR, while a separate random password is logged and never used. A security decision on initial-password generation and delivery is needed before this process can be built.

If this is not answered: A unique random password per account, change forced at first login, delivered by a separate channel agreed with IT; no password in emails or logs.

Which Active Directory server should the new process connect to, over which connection type, and which IT team will set up its service account in Boomi?

The production AD host, port and protocol and the bind account are not in the export.

If this is not answered: LDAPS on port 636 to the production domain controller, service account configured by TaskUs IT.

Who should receive the "AD user created" notice for Philippine hires and for US hires?

Hardcoded recipients (one OSI consultant for PH; five TaskUs HR/recruitment people plus the consultant for US) must be replaced by distribution lists. TaskUs to confirm the lists.

If this is not answered: The hiring manager plus the EmailDL "AD" list for PH, and the manager plus the EmailDL "UShrisJobvite" list for US.

When a new hire has the same first and last name as someone already in the same AD area, how should the account be named?

The account's directory name is "First Last" with no tie-breaker, so the second person's account cannot be created.

If this is not answered: Append the employee number to the display name for the second person.

If a returning employee still has a disabled AD account, should that account be re-enabled or should a new account be created?

Today a disabled account is ignored and a new one is attempted, which can clash with the old account name.

If this is not answered: Report the case to the IT service desk and do not create a second account.

Should the IT service desk be emailed when an AD account cannot be created?

The failure notices exist but are switched off, so failures are only visible in the new-hire job's reports.

If this is not answered: Yes, send failures to the EmailDL "itservicedesk" list.

When a new hire's project is not in the OU and group tables, is placing the account in the general "Floating" area with no project group still correct, and should anyone be told?

The project tables are maintained by hand; missing projects silently fall back to the Floating area.

If this is not answered: Keep the Floating fallback and include such accounts in the success notice.

User stories

US-001 Day-one network account High

Role: New hire and their manager

As a hiring manager I want my new hire's AD account created in the right OU and groups so that they can log in on their first day.

  • Account created with sAMAccountName per the TaskUs rule and UPN <sAM>@taskus.prv
  • OU and group follow the project-ID tables for the worker's country and grade
  • Manager attribute set when the manager exists in AD
  • The person must change the initial password at first login

Security

AspectDetail
Fixed initial passwordEvery new account receives the same hardcoded unicodePwd literal, and the four success-email variants include it in the message body.
Generated password logged and returnedThe random password is written to the BPEL audit trail and returned in TransmissionAck ReferenceValues/Value; the new-hire job emails it on one error path (see newhire-emp-sch).
Weak random sourcejava.util.Random is not cryptographically secure.
Unescaped LDAP filter and DN valuesNames and IDs are concatenated into search filters and the DN without escaping; commas or parentheses in names break the request.
Hardcoded recipientsSuccess emails go to named individuals (TaskUs HR/recruitment and an OSI consultant) hardcoded in the BPEL instead of EmailDL keys.
Plain HTTP inboundThe service endpoint is http:// on port 80.

Process flow

Step by step

  1. Receive new hire — EmployeeEBM from newhire-emp-sch
  2. Enrich from HCM — OTBI by person number
  3. Search AD by employeeID — VerifyUser
  4. Active account exists? — count 0 or Disabled Accounts = new
  5. Update mail, return Existing — ADEmailUpdate
  6. Find manager in AD — employeeID, then "Ma. " fallback
  7. Derive OU and department — Country / grade / project tables
  8. Create AD account — LDAP add
  9. Account found after add? — ConfirmUser count contains 1
  10. Fault: return Failed — catchAll; notification skipped
  11. Return Failed — Notification skipped
  12. Enable account — UPN, password, UAC 512
  13. Add to groups — Wi-Fi (SA-) and project group
  14. Load HCM user name — hcm-create-user-dat, async
  15. Notify manager and HR — Hardcoded recipients
  16. Return Success — Callback TransmissionAck

Not analysedThis interface owns no profile components: the request and response use the EmployeeEBM and TransmissionAck profiles of hcm-dat-generation and the OTBI rowset of hcm-otbi-sql-query; LDAP request/response shapes come from the connector.

How it is built today

Async BPEL composite called by ProcessNewHireEmpReq_Sch. It calls ProcessHCMExtractSyncProv (MDS WSDL) for OTBI, five LDAP adapter references on eis/ldap/TestConnection, ProcessCreateUserDAT (async, MDS WSDL) and XXSendNotification, uses seven MDS DVMs and an embedded Java password generator, and returns a TransmissionAck by WS-Addressing callback. ProcessCreateADUser_temp.bpel is present but not wired in composite.xml.

How it should be built in Boomi

Boomi sub-process "AD User CREATE" called synchronously by the new-hire process (a Web Services Server listener only if other callers exist). Steps: Process Call hcm-otbi-sql-query; op-ldap-search; decision; manager search; cross reference lookups; map-ebm-to-ad-user; op-ldap-add; op-ldap-search confirm; op-ldap-modify for enable and groups; Process Call hcm-create-user-dat; notification through util-send-notification to EmailDL keys; return the TransmissionAck. Password handling per the security decision; no password in logs, emails or the response.
