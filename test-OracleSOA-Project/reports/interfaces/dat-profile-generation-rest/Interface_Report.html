Purpose

Post-load reconciliation and follow-up for recruited hires, exposed as REST service JobVite_Rest (POST, Employees JSON). For each candidate it looks up the HCM person number; if found it updates the Jobvite candidate with hcm_integration_status=Success and the employee ID, otherwise it fetches the HDL load errors (via the candidateID->contentID cross reference) and updates Jobvite with status Error and the message. It writes and emails HCM and HRIS list reports, appends success/failure rows to the daily Jobvite consolidated file, and for the batch builds Salary.dat and TalentProfile.dat, starts the HCM Data Loader and calls the payroll allowance loader.

Business context

Closes the loop between Jobvite and HCM after hcm-dat-generation has loaded the worker: Jobvite shows whether each hire reached HCM, HR receives lists of created hires, the 23:30 consolidated notification job reports the day, and salary, talent profile and allowances are loaded. Called by int-file-intake / jobvite-create-employee-rest three minutes after each hire; the same core is reached by the archive poll (dat-profile-archive-poll).

Summary

After a hire has been sent into HCM, this service checks whether it worked and finishes the job. For each candidate it asks HCM for the new person number. If HCM has the person, it marks the candidate in Jobvite as successfully integrated with their employee number. If not, it looks up the HCM Data Loader errors for that candidate's load and writes the error back to Jobvite. Either way it emails HR lists of the hires (one detailed list, one HRIS summary) and adds a success or failure line to the day's consolidated file, which a nightly job sends out at 23:30.

For the hires that succeeded it then creates two more HCM data files (salary, using a salary-basis table by location, and talent profile with up to three previous employers) and starts the HCM load, and it sends the allowances to the payroll allowance service.

Several points need attention. The Jobvite API key and secret are written in the service address and must be replaced. The detailed HR list contains salary, visa and tax ID data and is emailed as an attachment. The country check sends lists to both the Philippine and US recipients whenever both country fields are filled, which is almost always. The payroll call identifies employees by SSS number while the real HCM person number is available. Error text is carried in an unrelated field ("ContractEndDate"). Four versions of this service exist; one of them also creates Google accounts, so TaskUs must confirm which is deployed.

Key points

  • Inbound REST JobVite_Rest: POST /, JSON Employees (ReadFileService layout); immediate empty reply; no OWSM policy in the project (no wsm-assembly).
  • Per candidate (sequential): ProcessGetPersonNumber(National_Id = SSSNo, CandidateID = ID prefix, Effective_Start_Date) and wait for callback.
  • Found: EmployeeID := person number; FirstAppliedTime := flow ID; ContractEndDate cleared; xref:markForDelete XRef_UCMID; Jobvite PUT hcm_integration_status=Success, hcm_employee_id.
  • Not found: ContentID := xref:lookupXRef(XRef_UCMID candidateID); getHDLErrors; message = first MSG_TEXT or "Failed during Importing the details, Please Verify once again"; stored in ContractEndDate; Jobvite PUT status Error with details.
  • Lists: HCMList_<ts>.csv (all input fields) and HCMList_hris_<ts>.csv (Date, InstanceID, User, EID, Department, ProjectID, JobTitle, LocationName, Error, Message) in Domain.dvm "Email" folder; FileNotification to EmailDL HCMListEmail/USHCMListEmail and hris_Jobvite/UShrisJobvite.
  • Batch (if any success): Salary.dat (SalaryBasisName via Salary_Basis.dvm on location), TalentProfile.dat (profile + up to 3 PREV_EMPLOY items) in Domain.dvm "DatFiles" folder; ProcessHDLProvABCSImpl (dDocTitle Worker) and ProcessPBLProvABCSImpl, both without waiting.
  • Consolidated rows (EmployeeId, CandidateId, names, Status, Message) appended to JobviteConsolidate_PH.csv or _US.csv (Append true).
  • Jobvite PUT URL https://api.jobvite.com/api/v2/candidate with api and sc keys in the query string [redacted].
  • catchAll: EmailDL notification with raw fault text (no "@!-" format).

Client questions

Which version of the new-hire follow-up service is running in production: the Jobvite version, or the version that also creates Google accounts and updates the work email?

Four variants exist. The GSuite variant additionally creates Google accounts here and updates the HCM work email; if that variant is live, Google accounts for recruited hires are created in this flow and not only in newhire-emp-sch. Confirm which variant is deployed.

If this is not answered: The Employee_JobVite version (no Google creation here).

Where should the day's hire results be kept for the 23:30 summary job once the server files go away?

Legacy appends consolidated rows to JobviteConsolidate_PH.csv / _US.csv on the server for the 23:30 job to pick up. Decide the Boomi staging mechanism (a database table, or a document cache plus the day's executions).

If this is not answered: A small database table, written per hire and read and cleared at 23:30.

Can TaskUs issue new Jobvite API credentials for Boomi and revoke the ones in the current integration?

The Jobvite api and sc keys are embedded in the reference URL in composite.xml (redacted) and must be rotated and re-issued for Boomi.

If this is not answered: New keys issued and stored in the Boomi Jobvite connection.

Should the HR hire lists go only to the team for the hire's country?

The legacy country condition also sends to both PH and US lists whenever both Country and CountryCode are populated, which is probably a defect; confirm the routing.

If this is not answered: Send only to the hire's country team.

Does the detailed HR list need salary, visa and tax ID data, given that it is emailed to a distribution list?

The list contains every field of the hire record.

If this is not answered: Reduce the list to identification, job and status fields.

Should allowances be loaded using the HCM person number rather than the SSS number?

The payroll allowance load identifies employees by SSS number, while this service already knows the real person number.

If this is not answered: Use the HCM person number.

Process flow

Step by step

  1. Receive candidates — REST JobVite_Rest
  2. Next candidate — Sequential
  3. Look up person number — hcm-get-person-number
  4. Found in HCM?
  5. Notify error — EmailDL notification
  6. Jobvite: Success — PUT candidate
  7. Fetch HDL errors — XREF + hcm-get-hdl-errors
  8. Jobvite: Error — PUT candidate
  9. Write and email lists — HCMList / HRIS by country
  10. More candidates?
  11. Any success?
  12. Salary, talent, HDL, PBL — No wait
  13. Append consolidated rows — PH or US file
  14. End

How it is built today

BPEL composite with a pick on REST JobVite_Rest or the inbound File adapter, sequential loop with async calls to GetPersonNumber and getHDLErrors, REST PUT to Jobvite, five File adapters, FileNotification, and fire-and-forget calls to the HDL and PBL loaders; SOA XREF for candidate->content. Variants: Employee (older, no Jobvite update or consolidated file), GSuite_Java_Process (adds Google user creation, work-email update and an attachment file), Employee_JobVite (baseline).

How it should be built in Boomi

Boomi listener "DAT Profile Generation REST Listener" (Web Services Server, JSON, authenticated) calling "Sub: DAT Profile Generation Core" (shared with dat-profile-archive-poll): per candidate hcm-get-person-number, hcm-get-hdl-errors via the agreed content-ID store, map-int-to-jobvite-status + op-jobvite-put-candidate on conn-jobvite-api, map-int-to-hcmlist + util-file-notification; batch maps map-int-to-salary-talent-dat -> Process Call hcm-hdl-loader, map to EBM -> Process Call hcm-pbl-allowances; map-int-to-consolidated rows written to the agreed staging store for the 23:30 job.
